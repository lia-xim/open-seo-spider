# Crawl control and recovery

`POST /api/crawls/{id}/pause` stops admission of new documents and drains admitted work. The API first returns `pausing`; active requests, redirects, browser navigation and native PDF parsing may still finish. It publishes `paused` only after those documents and discovered work have committed, a terminal SQLite checkpoint is saved, and the report/revision/manifest projection succeeds. A pause is idempotent. Cancellation can escalate a draining pause and retains the existing abort semantics; started blocking work may outlive an aborted caller.

Page documents and sitemap/robots discovery units have separate durable frontiers. A pause during discovery completes the currently admitted unit, atomically stores its children/page candidates and leaves later units pending. It does not mark discovery complete simply because work stopped. API `stats.queued` counts page documents and `stats.discovery_pending` counts discovery units at a terminal checkpoint. Progress during active discovery also includes admitted/discovered work. A configured sitemap limit yields `limited` with unfinished discovery, rather than a false completed discovery marker.

`POST /api/crawls/{id}/resume` starts a new generation from committed fetch identities. It rejects `running`, `pausing` and `cancelling`, imported snapshots without a saved SQLite frontier, and manifest-only projects. A missing or invalid frontier accompanying a paused/running manifest becomes an explicit recovery error; captured historical JSON remains available. Top-level `resume_available` describes the validated local frontier and current lifecycle. A historical report alone is not evidence of resumable work.

An omitted resume body preserves saved settings. Optional JSON can change only `max_pages`, `concurrency`, `delay_ms` and `request_timeout_secs`. An explicit `max_pages: 0` removes the operator page limit; omission keeps it. Settings validate before state changes or archival. Scope, credentials, robots, rendering, extraction and other discovery semantics remain fixed within a job. An unchanged exhausted limit can immediately produce another limited checkpoint.

SQLite records the active generation and terminal revision/outcome together with its core report and SHA-256 hashes. `checkpoint.report_sha256` hashes the compact core report in SQLite; it does not describe the separately extended app JSON export. `checkpoint_valid` verifies controlled-writer checkpoint consistency against saved hashes, generation/outcome and frontier counts. It is not a general integrity check for arbitrarily edited SQLite rows.

Startup inspects SQLite read-only, recovers paused/completed/limited/cancelled checkpoints and interrupted committed work, and performs no website requests. SQLite-only jobs with no JSON or manifest are recoverable. Active generations without a terminal checkpoint become `interrupted`; a process crash never proves that a graceful drain completed. Current app analysis may be rebuilt in memory from a valid core checkpoint; startup never rewrites historical JSON bytes, whitespace or unknown extension fields.

Each successfully published generation has an immutable app report under `snapshots/{id}/generation-{generation}.json`. Explicit resume archives the exact prior current-report bytes to a unique `before-resume-*.json` before replacing that current projection. Generation checks reject stale event or terminal publication, and the job write lock covers terminal projection writes. SQLite and filesystem writes are separate transactions: projection failures remain visible, and startup reconciles against committed SQLite evidence. Exactly-once remote requests and power-loss durability are not claimed. Uncommitted interrupted requests may repeat; committed page results are retained.

The pure `CrawlControl`, `run_controlled`, checkpoint inspection and original HTTP/browser/parser fixtures are independent implementations. [API/CLI acceptance script](../scripts/crawl-control-e2e.mjs) exercises real held-request barriers, byte preservation, missing-frontier errors, SQLite-only recovery, discovery pause and explicit operator-limit resume. Its recorded result is separate from authored test expectations and full reference-product parity remains `NOT_PROVEN`.

Primary lifetime reference: [Tokio `spawn_blocking`](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html). A started blocking task cannot be cancelled merely by dropping its waiting future; the actual blocking-parser fixture verifies that graceful pause waits for it.
