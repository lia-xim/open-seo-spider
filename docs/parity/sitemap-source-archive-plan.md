# Durable sitemap source bodies: proposed next slice

Status: **DESIGN ONLY / NOT IMPLEMENTED / NOT RUN**. This document reads the immutable SourceV4 snapshot `45a07ef277cf1ffef5ff8d577fe05dc48ee1d84548ada2d8453aaf859a5d26b3`, commit `f828ad133e0d5f8d32ee4fcf90bdb4611bd35924`. It does not change that source, execute any target, or confer installation/feature-parity acceptance. All names, new limits, routes and states below are proposals unless explicitly described as existing.

The smallest useful next feature is an independent opt-in archive of the bytes the crawler actually observed: the post-HTTP-decoding entity, and the successfully file-decoded XML bytes. Bodies belong in bounded local binary files, with small SQLite descriptors tied to existing source measurements. They must remain readable after restart without contacting the website. Membership completion, source counting and body availability remain separate facts.

## What currently exists

* `crates/core/src/sitemap/models.rs:209-216` has `SitemapEntityDecode.xml: Vec<u8>` with `#[serde(skip)]`. The XML is parser input, not durable report data. `sitemap_discovery.rs:10-32` projects decode facts into the source document; it does not retain a raw body.
* `crawler.rs:3351-3396` receives `response.chunk()` bytes after reqwest HTTP Content-Decoding, counts every returned chunk, retains at most the configured entity cap and marks truncation. `capture_for_config` receives the actual slice. The body Vec leaves scope after the protocol observation is returned. `crawler.rs:2881-2907` counts and parses the successfully decoded XML Vec, then keeps the decode object only in the private observation.
* `sitemap/entity.rs:95-149` hashes successful gzip `Read::Ok(n)` outputs, observes the true EOF and refuses the real over-cap sentinel. Bytes possibly written into a buffer by `Read::Err` are intentionally neither counted nor hashed. The successful output is returned at `:215-221`; failed output Vecs are not exposed for recovery. File-gzip validation includes all members/trailers/CRC and trailing/nested-gzip refusals. HTTP gzip and file gzip are different layers.
* `sitemap_source_schema.sql` contains measurement and measurement-to-document association tables with compact JSON and SHA fields. It has no body/BLOB/file-reference table. Measurement JSON is capped at16KiB; its source catalog is32MiB. The separate membership catalog can explicitly be128MiB. Neither is a body-storage allowance.
* `store.rs:1324-1360` commits measurement transaction A and only then confirms its in-process receipt. `crawler.rs:1605-1656` does this before membership/admission transaction B. `store.rs:1419-1490` keeps membership/frontier/link writes together. B failure deliberately leaves A visible and unjoined. This invariant must survive the new feature.
* `content_binding.rs:31-110` has source/config/generation/hash bindings and extracted content, not original-body files. `content_capture.rs:55-103` has HTML8MiB, text512KiB and result-JSON4MiB defaults/hard ceilings. Raising these would change a separate feature and would still not recover the XML bytes.
* `server.rs:458-460` truthfully advertises `body_retention:false`, `entity_body_retention:false`, and `raw_xml_body_retention:false`. These must remain false in SourceV4 and until a later implementation and actual acceptance warrant more specific capabilities.
* `generation_export.rs:94-121` is a useful publication pattern: unique same-directory temp, `create_new`, write, file sync, new-name hard link, and own-temp unlink. It does not provide a filesystem+SQLite transaction or a general directory-entry power-loss guarantee. The fixed `.tmp` `write_json` at `server.rs:1510-1515` is not a suitable archive primitive.
* `mcp/files.rs:333-388,839-944` provides examples of capability-relative nofollow directory traversal, owned staging identity checks and explicit directory-durability qualification. Its public1MiB UTF8-write/32MiB observation caps and tool contracts must remain separate. Core cannot import an App module.

## Byte semantics and configuration

Proposed field on `CrawlConfig`: `sitemap_source_archive: Option<SitemapSourceArchiveConfig>`, absent/null omitted when serialized. Absence keeps every old configuration byte/hash and legacy reopen behavior; it creates no body directory. `{}` explicitly enables these defaults:

```json
{
  "sitemap_source_archive": {
    "retain_post_http_entity": true,
    "retain_decoded_xml": true,
    "max_bytes_per_body": 67108864,
    "max_total_body_bytes": 536870912,
    "max_capture_records": 4096
  }
}
```

These are proposed archive defaults, not actual SourceV4 fields. Validate strict object shape, booleans, positive integers, at least one selected representation, per-body hard ceiling64MiB, total hard ceiling8GiB, capture-record hard ceiling100,000, and all checked arithmetic before I/O. A capture record has at most two representation descriptors. Cap the new descriptor catalog separately at32MiB and each descriptor at8KiB; do not weaken the existing measurement/catalog/row/export limits. Disk accounting charges each physical published file, including both equal-byte plain-XML representations unless a later explicitly tested dedup design changes it. Default512MiB permits four maximal128MiB pairs, subject to descriptor/count limits. A lower user quota yields an explicit archival omission.

Use the same strict-map/Option/skip-None pattern already reviewed for `sitemap_source_processing` and `sitemap_membership_limits`. All API create DTO/config save/reopen, CLI `--config`, MCP start-tool schema, capabilities and UI advanced controls must carry it. UI-only enable/limit fields must be stripped from the native request. The saved setting must survive reopen/reload and disabled-again must omit the field. Direct Serde duplicate-key rejection is distinct from raw HTTP `Json<Value>` coalescing, as with the existing controls.

The archive and source-processing profiles are independent. Requesting archive64MiB does not increase the legacy8MiB input clamp; requesting processing64MiB does not enable archiving. To capture a50MiB or64MiB full source, the operator must explicitly select sufficient source entity/XML work limits and archive/disk limits. Membership128MiB is a third independent option; even a full body does not guarantee complete retained member rows or every50k source. Parser field/text/event/depth limits and the protocol50MiB/50k assessments remain unchanged.

| Representation | Exact meaning | Permitted completeness claim |
|---|---|---|
| `post_http_entity` | Exact bytes returned by reqwest after Content-Decoding, before file-gzip detection; may still be a gzip file entity | `complete` only on the actual full HTTP body. Otherwise `observed_prefix` with exact retained prefix length/SHA and separate received lower bound. |
| `decoded_xml` | Exact identity/file-gzip decode output; preserve BOM, encoding bytes, CRLF, comments, entities, whitespace and declaration without rewriting | `complete` only for successful existing decode with matching complete SHA/length. XML parse validity and membership retention remain separate. |
| `wire_entity` | Compressed HTTP wire/framing bytes | **Not captured or reconstructable by this proposal.** Reqwest has already decoded that layer. |

A complete HTTP503 body may be archived as `post_http_entity` diagnostics with status503, but never called a successfully decoded sitemap. A CRC-bad complete file-gzip entity may be archived as complete post-HTTP input while decoded XML stays unavailable/failed. Incomplete post-HTTP prefixes can be retained with `extent:observed_prefix`; never pad, reconstruct or mark them complete. Decoder-failure output prefixes are not recoverable from the present error outcome; v1 leaves that representation unavailable and retains its existing measurement hashes only. No inspection of unreturned Err buffers is allowed. Preserving failed decoded-prefix bytes is an explicit later seam/test gate, not implicit success.

## Proposed storage and integration

Use a new narrow Core archive component (`sitemap_source_archive.rs`, models and schema), with capability-relative nofollow operations. Pin the same already locked `cap-std`/`cap-fs-ext` versions if adding Core dependencies; do not refactor or enlarge MCP file tools. Core must retain/inject the actual database location or an owned archive capability because `CrawlStore` currently stores only a Connection mutex. Do not make a remote URL, imported report path or user-supplied relative artifact name filesystem authority.

For an App database `data/<uuid>.sqlite`, derive the owned sibling `data/<uuid>.sitemap-bodies/`. For a CLI database, derive the analogous sibling from the already opened database path. Create it only for a writable, validated, opted-in crawl. Read-only open never creates directories/tables, repairs a missing initialized catalog, or fetches a URL. Anchor/hold the directory capability through all operations; reject symbolic links/junctions in every ancestor and nonregular leaf; do not rely on `canonicalize` then reopen. Generated hash-only relative file IDs have no caller-controlled path components. Native Windows and supported Unix proof are separate gates.

Inside that root, use unique generated temp names and immutable binary object names. Proposed `body_id` is a domain-separated digest of measurement ID, representation, extent, exact byte length and content SHA. No cross-job global content sharing or reference counter is needed. A preexisting final name is verified byte-for-byte/length/SHA before any idempotent reuse; it is never overwritten. No compression, charset transcoding, canonicalization or JSON/Base64 body storage is introduced.

Proposed descriptor fields: version/profile, body ID, measurement ID + exact envelope SHA, staged document SHA, requested task identity, capture-config SHA, capture generation, source revision, representation/extent, retained byte length/SHA, actual receive/decode precision, HTTP/decode status, and relative object ID. Store a bounded canonical descriptor JSON/hash plus indexed identity columns. Preserve the original requested URL; final URL/status is separate, and no alias or hash is a permission grant. A new catalog summary binds descriptor count/bytes, physical charged bytes, revision/digests, initialization config and first durable omission. A descriptor inventory page is bounded independently of binary files; a missing body is never a successful empty inventory.

**Chosen transaction ordering: existing A, archive A_body, existing B.** Keep the current measurement envelope and A/B receipt/hash contract unchanged; adding file state into its16KiB JSON would be the wrong boundary.

1. While the successful private fetch owns the original post-HTTP Vec and decoded XML Vec, transfer ownership into an optional private `SourceBodyCandidate`; do not clone64MiB buffers or reconstruct from parsed entries. Add an unpersisted carrier through protocol observation/`DiscoveryOutput`. Pure decoder/parser helpers remain free of filesystem I/O. Once parsing/batch projection no longer needs XML, move the Vec with `take`, retain compact existing facts, and transfer the candidate to the archive writer. With config absent, preserve the current drop path.
2. Commit and confirm existing measurement A exactly as today. If A yielded a fixed omission instead of an actual measurement row, no body may be advertised as measurement-bound. Leave a bounded archive omission/unknown marker and dispose only the owned candidate/staging. Do not invent a measurement ID from the expected document ID.
3. Validate the committed measurement/seal/config/generation and still-pending source in one read/guard context. Reserve per-job archive count/byte quota before disk work. A bounded owned writer (initially one archive writer per crawl) hashes actual slices while writing generated same-directory `create_new` temps, syncs them, and verifies actual EOF/length/fullhash. Publish a complete immutable new name using no-overwrite semantics. The current serial discovery path already bounds source-unit concurrency; new cancellation must still await every owned writer/handle, not detach a blocking task.
4. In **A_body**, bind the sealed files to the exact already committed A record and current saved generation/config/pending source; insert all successful representation descriptors and quota/omission summary in one SQLite transaction. Whole-attempt quota planning is all-or-none for the selected available representations; do not retain one half silently when a pair cannot fit. Expected byte/count quota refusal is a structured archival omission and can leave normal B behavior intact. Unexpected permission/I/O/hash/sync/schema failures remain errors and stop the unit before B; A stays readable. Only after A_body commits may readers see a `retained` descriptor. A crashed/interrupted capture with no A_body record is unavailable, never known empty.
5. B continues to atomically commit membership/frontier/source-association using its original A receipt. A_body descriptors reference the measurement, not a mandatory membership document, so **B rollback must preserve both A and an already committed A_body**. A full source body may be available even when membership32MiB/row/retention limits reject B. Neither body storage nor a complete hash attests membership completion or source freshness.

File publication and SQLite cannot be one transaction. Publishing sealed files before A_body avoids committed references to partial files, but a crash before A_body commit can leave complete unreferenced orphans. This is an acknowledged recovery state. Do not advertise global FS+DB atomicity or unconditional power-loss durability. File sync and validated reopen are requirements; directory-entry sync/support must be recorded accurately per platform. If that durability is not proven, expose that boundary instead of fabricating it.

Failure cleanup removes only a held-identity temp/new file owned by the failed uncommitted operation and never a preexisting verified object. If cleanup identity is uncertain, retain and report it. Once A_body committed, no failure path deletes its object. Retry after A/A_body interruption revalidates the exact old record and may reuse only verified identical immutable content; it must not relabel a failed attempt, overwrite an existing descriptor, or mutate prior A measurement JSON. If archival attempt history is needed, append a separately bounded attempt sequence rather than rewrite a failure as success.

## Reopen, offline API and transport budgets

On reopen validate the archive marker/schema/bounded SQL lengths before allocating JSON, descriptor canonical hash/index consistency, associated measurement envelope/config/generation/seal and aggregate quota/digest. Open each requested file through the retained nofollow root, require a regular file and actual bounded handle read, and verify exact full length/EOF/SHA. A directory entry/hash alone is not recoverable bytes. Partial/corrupt schema is an error, not auto-repair. Legacy absent archive/config means `not_recorded_or_legacy_unknown`; a current initialized catalog with an absent expected object means unavailable/corrupt, not empty. Checkpoint/report load/inspection and selected initialization must validate new metadata roots; full file verification is done before claiming actual body availability/access, not by reading every body for an unrelated status call.

Proposed metadata endpoint `GET /api/crawls/{id}/sitemaps/source-bodies?measurement_id=...` returns a small versioned envelope with source context, descriptors, local availability/unknown reasons and `website_requests:0`. It does not inline body bytes or leak absolute paths. Support separate native-vs-declared-import provenance, as with content access. The selector binds job UUID, current access generation/config, origin measurement/generation, representation and archive revision/digest; current/parent captures cannot be relabelled. A stale/foreign cursor is an explicit409/4xx, not a new live source fetch.

Proposed binary route `GET /api/crawls/{id}/sitemaps/source-bodies/{body_id}/download` uses `application/octet-stream`, attachment filename generated from the ID, `nosniff`, and no content transformation/HTTP compression. To avoid a mutable source-file check/read race and late-corruption false success, first create an owned bounded **verified spool** from the held source file, hash+length+true-EOF check it, and read it back before sending success headers. Use an anonymous/unlinked or platform-protected owned temp handle; stream the same held verified handle rather than reopen a caller-visible path. At most two read sessions globally and64MiB per spool imply at most128MiB temporary payload disk, plus64KiB buffers. Check `SitemapReadControl` while reading/hashing/writing; maintain real worker/disconnect/EOF/handle-close evidence. Scratch I/O is explicitly allowed and separate from user-data writes; this is a zero-website-I/O API, not a claim of zero filesystem writes. Source/user files remain unchanged. Directory/spool handle containment and cleanup on Windows and Unix need actual native proof; no claim against arbitrary hostile same-user memory/disk access.

Keep8MiB ordinary JSON and64MiB existing CSV boundaries unchanged. This **new binary download** has a separate explicit64MiB limit; cap+1 is rejected before publication. An existing full-body hash is checked against actual stored bytes, not trusted as proof. Stream read failures after headers must abort without a successful complete EOF; clients/CLI verify declared length plus descriptor SHA before finalizing output. A CLI cold-reader copies through the same verified handle to a unique destination and atomically publishes a new name only after full final hash/length success; no overwrite/console UTF8 conversion.

For MCP, do not Base64-encode64MiB into one JSON/RPC message. Extend the existing sitemap tool with strictly typed, mutually exclusive archive metadata/read operations or add separately reviewed explicit tools. If byte windows are exposed, use bounded verified-spool sessions,256KiB windows, session/role/descriptor-bound opaque cursors, fixed short expiry, bounded session slots, and close on EOF/explicit close/disconnect/cancel/expiry. Hash the source once into the owned immutable spool, then page that exact handle; do not rehash64MiB for every small page (a new quadratic path). Exact future inventory/schema changes require new SDK tests; current26/31 file-tool inventories remain SourceV4 facts, not silently updated expectations. The first binary/UI slice can ship only with MCP body access honestly unavailable until its own gate passes.

## Selected inheritance, portable reports and cleanup

Selected recrawls currently clone semantic config except four operational knobs and inherit source catalog/measurements from the sealed parent snapshot. They do not execute sitemap discovery. Preserve that: the archive profile is a semantic field, origin generation remains the parent's, and child access context remains its own current generation. Add an inherited archive basis bound to the exact parent snapshot/descriptor catalog. For a native parent-to-child operation, copy/verify immutable bytes into the child's new owned archive before committing selected initialization; descriptors retain origin identity but point to the child-owned copy. This avoids a dangling parent-folder dependency and mutable cross-job hard links. Charge the inherited physical bytes to the child's unchanged archive quota. Initialization rollback leaves no committed references and cleans only owned staged child entries. No new source capture is inferred.

A JSON report containing hashes/descriptors does **not** contain or recover the bytes. Existing report/recrawl input has its own256MiB bound; never inline bodies there. A JSON-only import retains declared historical descriptors but exposes `local_body_available:false`/`external_bytes_not_supplied` separately, never silently follows imported absolute/relative file paths. A user backup/recovery must copy the database plus its archive directory and verify both. A later optional portable archive bundle should include an explicit manifest, exact binary bodies and their hashes, use bounded streamed export/import, refuse traversal/links/duplicates/zip inflation/oversize, and publish an isolated new archive only after validation. That bundle is a separate acceptance item; until implemented, full portable raw-source recovery is NOT PROVEN.

No automatic broad cleanup is required for the initial feature. Read-only paths never delete. A later explicit offline archive-GC operation takes the job/capture lease, validates the committed descriptor catalog and every relevant owned-name/native identity, offers a concrete orphan inventory, and can delete only its own unreferenced generated temps/objects. It never traverses outside, follows links, deletes parent archives, or infers an orphan from filename shape alone. Commit a durable tombstone/removal transaction before a deliberate retained-artifact removal so an interrupted delete cannot remain advertised as available; active read sessions hold their own spools. Missing/corrupt referenced files remain reportable evidence and are not automatically wiped or refetched. Full user-data deletion needs its own explicit operation and is not implied by GC.

## Acceptance and remaining limits

`TODO.json` is the concrete proposed implementation/verification sequence. Every item starts `NOT_IMPLEMENTED_NOT_RUN`. Main positive gate is byte-for-byte recovery after a real cold restart and through API/CLI/SDK/UI of genuine50MiB and configured64MiB captures, including the terminal byte, alongside measurement/membership/status truth. Native local server fixtures must independently retain exact expected wire/post-HTTP/decoded witnesses and actual child closes. Counts/hashes without stored and returned matching bytes do not pass.

This design makes none of those claims and does not change the current feature-parity ledger.
