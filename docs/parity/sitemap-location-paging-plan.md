For L locations and fixed visible limit b=200, P=ceil(L/b) pages each require at least a full raw pass over R ledger rows. The traversal therefore costs at least Omega(P*R), quadratic as L and R grow together. For L=50,000 and R at least100,000 Entry+Location rows, 250 pages entail at least25,000,000 raw rows in EACH repeated full traversal. The envelope-sizing pass alone logically serializes 250*59,613,930 =14,903,482,500 bytes under Root's reported catalog size. These are source-derived work counts, not physical disk-I/O, elapsed time or peak-memory measurements. The complete envelope, coverage, relation and saved-report passes add further work.

The ordinary current reader deliberately avoids retaining a complete raw catalog Vec. The problem is repeated proof construction and repeated decode/SQL/serialization, not an asserted59MB Rust catalog clone on every page. The App's final8MiB response guard, Core16MiB rich DTO guard, raw-window guard and CSV64MiB guard remain separate and must remain exact.

## Two implementation scopes that preserve evidence

The first scope is a stateless optimization with unchanged request semantics: share coverage counters with the actual raw validation pass; eliminate repeated decode of the same Entry with a bounded streaming relation strategy; derive the exact canonical envelope byte count during that same validated traversal with an oracle against the unchanged serializer; and use kind-specific/indexed continuation queries while retaining exact role/filter matching. Duplicate, order, row hash/canonical bytes, parent/source bindings, policy and full tail checks remain mandatory. This reduces constants but cannot remove the per-request full-proof lower bound. An index is a performance aid, never a substitute for import/corruption validation.

The larger scope is an explicit retained read-session engine. One worker keeps ONE actual read transaction and the real `PreparedSitemapRead`/private proofs alive across bounded page commands. Proofs stay inside the worker's callback stack. No public header clone, rolling-hash string, revision cache, deserialized DTO, unsafe self-referential object or lifetime transmute can stand in for that transaction. The existing `with_verified_sitemap_stored_rows` callback at `crates/core/src/store/sitemap_stored_rows.rs:86` demonstrates the ownership boundary, but currently exposes only fixed-filter complete visits. A future narrow borrowed window method would reuse its private raw and analysis proofs; it must not reopen Store or run a new preparation for every command.

Prefer ONE registered retained blocking worker owning TWO SQLite connections on that same thread: the data connection holds its read transaction; a persistent monitor connection performs short read-only checks outside any long transaction. This needs one Worker/Supervisor handle pair and avoids a two-task admission gap. If a background monitor is chosen instead, its real handle must join the same admission/drain cohort and remain retained independently. Neither variant exists in V4.

## Snapshot and mutation contract

A held read transaction by itself is insufficient to preserve current cross-request invalidation: it intentionally continues to see its old snapshot. SQLite documents that a WAL reader keeps its original view until the transaction ends. See [SQLite isolation](https://www.sqlite.org/isolation.html). Thus a session must use a NEW explicit engine/cursor profile, while retaining existing stateless tokens and their existing route/oracles. It must not silently reinterpret an old token as permission to serve stale snapshot pages.

For the session profile, capture an opening monitor epoch, actual App job generation/config hash and file authority, pin the data read snapshot, complete ALL existing raw/source/coverage/report verification, and recheck the monitor epoch and App identity before publishing readiness. Any committed mutation during that handshake makes the candidate session stale; it is not a valid cached context.

Each page command must bind session identity, caller/job UUID, engine, immutable filter, row-cursor role, original after-sequence, generation/config, raw config/revision/rolling hash, source context, coverage inventory, report/analysis context and full catalog-state digest. The same checks apply before accepting a continuation and before releasing its encoded response. Preserve exact existing sequence continuation validation and same-filter role checks. Snapshot equality never means source-wide feature completeness.

On the SAME persistent monitor connection, compare `PRAGMA data_version` before and after each command against its opening baseline. SQLite documents that this counter changes for commits by other connections and that values from different connections cannot be compared meaningfully. A new monitor connection per request is therefore wrong. See [SQLite data_version](https://www.sqlite.org/pragma.html#pragma_data_version). The monitor connection must never make data commits. File replacement/rename/junction/symlink identity, schema and actual current App config/generation also require their own checks. A version change, identity uncertainty, unsupported monitor result, monitor error or lost connection closes admission and produces stale/failure; no cached-match fallback is allowed.

This monitor is NOT a cryptographic proof against arbitrary out-of-band same-inode file modification or restored timestamps, and a pathname-only metadata check does not prove that both SQLite connections opened the same file during a race. A real connection-to-file-identity/native Windows authority join is not supplied by the current code and is an implementation gate. If preserving the old raw-file corruption boundary cannot be proved, keep the stateless path fully verified or use a separately owned immutable SQLite snapshot artifact/one-operation streaming API with an explicit new contract; do not advertise full old-token compatibility. An artifact would add quota, validated copy/backup, cleanup and nofollow acceptance work and is not implemented here.

Within the supported SQLite-writer mutation model, page acceptance must have a clear linearization point at its fresh monitor/App check, comparable to the start of a new stateless read. Check again before response release; a change makes that reply stale even if its page bytes were already prepared. Tests must include mutations which keep the advertised summary/revision/hash unchanged, not merely honest new revisions. New generation, report-only writes, source-measurement commits and tail corruption must all invalidate. A more conservative all-write invalidation policy is a new-engine semantic change, not an invisible reuse of old tokens.

## Admission, memory and actual shutdown

Register the retained worker before opening SQLite or beginning the readiness handshake. Session shutdown must see sessions still starting. Keep all SQL Connection/Transaction/Statement and private proof lifetimes on that worker. Do not hold an App job read guard for an entire session or await worker drain while holding a guard the worker needs. Capture/compare App context for each bounded operation; the worker does not call back into the same locked CrawlStore.

Use a bounded command queue, one in-flight command and one bounded reply, with a server-wide and per-job session-admission limit. An initial implementation can permit one session globally and one per job until real memory behavior is measured. Never buffer the full ledger/report, all250 replies or an unbounded list of Location findings. Row/page limit200, exact App8MiB encoded response, Core/input/catalog/row/source/CSV caps and all unknown/failure distinctions remain unchanged. SQLite cache, JSON parser scratch, report value pages, WAL retention and operating-system memory remain outside an unmeasured Rust-allocation bound. Real RSS and SQLite/WAL workspace have to be measured; the design does not claim a hard RSS ceiling.

Validated idle and total-lifetime session budgets are required to release retained WAL snapshots and file resources. Their actual defaults/hard maxima must be chosen from future measurements before implementation acceptance. They are not a reduction of the current HTTP deadline or ongoing Large13 lease. Expiration is a Stop + actual close/join, not dropping a JoinHandle, clearing a map entry or claiming a worker exited.

Caller/EOF/close/expiry/shutdown must close command admission, set the actual `SitemapReadControl` stop/interrupt, and wake a worker waiting for commands. A full queue must not prevent Stop delivery. Abandoning a reply does not destroy its SQL worker. The worker finalizes current statements, ends the read transaction and closes both connections on its owning thread; the TaskOwner retains Worker and Supervisor handles until actual joins. Cancelling a drain waiter leaves both handles in their shared slots so another waiter can complete. Monitor/worker panic, SQL finalization/close error, missing exit/close or incomplete accounting remains sticky failure. If a separately scheduled monitor/timer exists it must also stop and actually join before success. No foreign PID kill, detached expiry cleanup or per-page spawn-and-forget blocking task is acceptable.

These ownership requirements were checked with the lifecycle author. Their unfrozen TaskOwner foundation can own a future session worker, but does not implement session commands, SQLite thread-local proof retention, monitor identity, memory budgets or session-close semantics. No current capability is inferred from that draft.
