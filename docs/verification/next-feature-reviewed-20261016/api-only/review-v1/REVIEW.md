1. **API-ONLY-01 / P2 — unnecessary mutable reference binding blocks the warning gate.** `source/crates/app/src/server/enrichment.rs:16` uses `move|mut channel,ready|`. Only the referred writer is mutated; the channel reference binding is never reassigned or mutably borrowed. This is a statically supported unused_mut warning under the project's -D warnings gate, not an executed compiler diagnostic. Remove only this binding mut and keep producer/ready_with_length behavior intact.

2. **API-ONLY-02 / P2 — ordinary CSV UI requests always choose an invalid column.** `source/web/api-enrichment.js:7` builds index0 for the visible 'first CSV column' option. Actual D3 `core/list_import.rs:319-321` accepts only indices1..16384; resolve_column keeps this one-based identity. Thus normal CSV preview/start refuses before provider use. Choose index1 and add a meaningful helper/consumer regression that asserts the ordinary CSV path's actual import contract, rather than only preserving a manually supplied header selector.

3. **API-ONLY-03 / P2 — reported Lighthouse runtime failures become Success.** `source/crates/core/src/api_enrichment.rs:100-104` accepts any Lighthouse object and ignores runtimeError. At140, Some(metrics) unconditionally becomes Success; absent individual metric fields do not prevent this. Therefore an HTTP200 body with `lighthouseResult.runtimeError` and no measurements becomes Success with all metricsNone, and an otherwise matching report becomes complete. Google documents runtimeError.code/message in the actual Lighthouse response schema. Handle this explicit provider outcome as a typed failed/unavailable observation; retain API HTTP200 separately and do not persist unbounded raw provider messages. Add a concrete200/runtimeError fixture and a no-metrics countercase. The [official PageSpeed v5 response reference](https://developers.google.com/speed/docs/insights/v5/reference/pagespeedapi/runpagespeed) supports the field distinction; this review inferred the erroneous local classification from source and did not call Google.

4. **API-ONLY-04 / P2 — deterministic normalized-URL byte refusal occurs only after job admission.** `source/crates/core/src/api_enrichment.rs:57-63` prepares/previews the plan without its8192-byte normalized URL guard; that guard is at112 and is first reached by run_api_enrichment at117. `enrichment_app.rs:43-48` has already created input/plan files, inserted the active job and returned a running job before the worker performs it. A raw UTF8 line under the import field cap can expand beyond8192 normalized ASCII bytes through percent-encoding (e.g.2000 `é` path characters). It is then a knowingly unexecutable plan, and a generic failed completion replaces useful preflight refusal. Apply this static URL-shape bound in common preparation before admission/store/provider work, keeping the worker's independent revalidation. Add Unicode normalized-byte boundary/+1 preflight checks and zero transport/store-admission evidence in the authored fixture. This is not a demand to relax the cap or silently drop one input row.
