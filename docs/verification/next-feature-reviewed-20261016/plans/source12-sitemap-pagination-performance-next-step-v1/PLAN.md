The index removes repeated scans inside one prepared request/CSV traversal. It does not amortize the250 separate HTTP preparations. Even a context-only row_limit0/page_limit0 request currently builds it eagerly before the later empty-output branch. A lazy index could avoid that case; it does not solve this250-window request because row_limit200 still has location analysis.

Recommended decision before implementation: first measure independent preparation counters over real repeated public requests (raw rows canonically decoded, report bytes hashed/visited, index attempts/commits/rows/fallbacks, SQL prepare/query counts), with exact same output/context/cursor bytes. Existing tests' counters are request-local and not a claim about actual runtime hot spots or RSS.

Then prefer one bounded service-owned snapshot session for an explicit continuation profile, reusing its actual owned read TX, verified context and private projection. Core's existing callback-bound prepared session is the starting seam; it cannot escape as a forged Clone/Serde proof. A dedicated owned blocking worker must own Connection/TX/index, accept only bounded page commands, have explicit queue/session/byte/idle/total limits, typed cancel/deadline interrupts, shutdown joins and exact release. Never keep borrowed transaction proofs across detached async tasks. Bind session token to job/config/generation/checkpoint/reportSHA/catalog revision+rollingSHA/source context/coverage inventory/reader+schema profile/filter/limit and original ordinals; refuse missing/expired/reopened sessions instead of silently changing snapshots.

Critical boundary: generation alone, TTL, file size/mtime or a cached reportSHA does not establish unchanged source bytes. Current code catches same-generation tail/report/ledger/source corruption on every new read. To retain that contract, a reusable projection needs a proved source immutability/write-epoch regime plus detection of all supported source changes (including other SQLite connections/replacement), followed by fresh verification on any change. SQLite data_version is an invalidation signal, not cryptographic authority; same-connection writes and physical replacement need separate guards. If this regime cannot be proved, keep full current verification for each public request and cache only derived work, accepting remaining O(N) cost. Serving a retained old TX snapshot is a different explicit snapshot contract, not an invisible substitute for present-source corruption checks.

A durable generation-keyed sidecar alone is therefore not the first patch. Any later sidecar must be disposable, versioned, bounded, atomically built/published after complete validation, tied to a strong full source identity, never authoritative over original rows/source document checks, and rebuild/fallback on mismatch. No source DB mutation during reads. Unsupported UTF8/SQL forms, budget/FULL/NOMEM retain exact original fallback; Cancel/I/O/corruption remain errors. Cache negative fallback classification only under the same proved identity, never hide changing damage.

Required future tests:250 public windows versus old exact outputs and complete tail membership; same-generation changed report tail, row body/canonical order/SQL indexes/duplicateIDs/source commits/checkpoint/config and whole DB replacement; valid source append/restart/selected-recall with stale cursor refusal; no silent reuse after cancel/deadline/session expiry/app reopen; zero/context-only lazy behavior; budget/FULL/NOMEM/unsupported UTF8 fallback equality; I/O/corruption not fallback; several callers bounded memory/session admission; slow/disconnected client, worker join and cold shutdown with no retained TX/lock. Root-only native comparison must keep genuine50000/250x200/fullCSV, cold/unknown states and zero website reads. No performance target or implementation completion is claimed here.
