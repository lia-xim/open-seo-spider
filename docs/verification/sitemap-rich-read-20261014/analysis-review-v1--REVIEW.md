## Confirmed P2: outer report key guard runs after large scratch allocation

However `ReportSeed::visit_map` line138 asks the serde deserializer to decode the complete identifier before invoking this visitor. The earlier bounded source `preflight` at line44 examines only `json_extract(report, '$.sitemap_source_measurements')`; it does not inspect the outer report's keys before the actual whole-report `ReportSeed` starts at line60.

Concrete source-level input shape: retain a valid current source envelope and all existing report fields, insert one unrelated outer key beginning with `\u0061` followed by approximately 100 MiB literal ASCII `a`, use a small value, and recompute the actual report/checkpoint SHA as the existing corruption fixtures do. The total remains below the256MiB report limit. JSON1's valid-envelope/source checks see valid JSON and the unchanged small source object. The later report key parser copies the approximately100MiB decoded identifier before the visitor rejects its length.

This allocation order is established by the actual locked `serde_json 1.0.152` source: `de.rs:2219–2223` clears scratch then invokes `parse_str` before `visit_str`; `read.rs:521–529` appends the remaining literal suffix to scratch after the early escape has forced the copied-string path. This is not merely a theoretical clone in an error formatter. It is a bounded-input but large Rust heap allocation before the intended per-key protection.

The result still rejects the malformed resource-profile input; this finding does not claim source-tamper acceptance.
